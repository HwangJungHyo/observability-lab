# 8-5 부하 시험 결과: smoke와 단계 부하

작성일: 2026-10-03 KST. 브랜치: `lab/008-integrated-incident`.
근거: 사용자가 제공한 k6 실행 출력과 docker stats 텍스트. 새 부하를 실행하지 않고 기존 결과를 정리했다.

## 1. 판정

smoke 2회와 1→3→5 VU 단계 부하를 수행했다. 단계 부하 2,080건은 HTTP·응답 본문 검사에서 모두 성공했고 중단된 반복은 0건이다. 유지 구간 p95는 약 83~84ms였다.

**이번 조건의 5 VU 범위에서는 뚜렷한 성능 저하를 관측하지 않았다. 최대 수용량·장기 안정성·급증 후 회복을 검증한 것은 아니다.** 급증(spike)·지속(soak)·한계 초과 스트레스 시험은 미실행으로 남기고 이번 장의 부하 실습을 종료한다.

## 2. 조건과 실제 적용 근거

| 항목 | 내용 |
|---|---|
| 생성기 | grafana/k6:1.3.0 임시 Docker 컨테이너 |
| 호출 경로 | k6 → Compose 기본 네트워크 → order-api:8080 → payment:8081 |
| 부하 모델 | ramping-vus, 요청 종료 후 각 VU가 0.2초 대기 |
| 요청 | POST /orders, amount=10000 |
| 성공 기준 | HTTP 201, status=confirmed, amount 일치, 주문·결제 ID 존재 |
| 설정상 대상 자원 | 앱 각각 CPU 0.5개 상당·메모리 512MiB·스왑 미허용 |
| 설정상 생성기 자원 | CPU 1개 상당·메모리 512MiB·스왑 미허용 |
| 실제 확인된 제한 | docker stats에서 두 앱의 메모리 상한 512MiB |
| 미확인 제한 | 앱 CPU·스왑, k6의 실제 적용값은 inspect 출력 미제공 |
| 자동 중단 설정 | 30초 이후 누적 실패율 5% 이상 또는 누적 HTTP p95 1000ms 이상 |

자동 중단을 실제로 유발하지 않아 동작 검증은 미완료다. 요약 파일의 expected 설정값은 실제 Docker 설정 확인을 대신하지 않는다. 자원 제한 파일이 있다는 사실만으로 전부 적용됐다고 기록하지 않는다.

VU는 고정 RPS가 아니다. 응답이 느려지면 같은 VU에서도 요청률이 감소한다. k6의 http_req_duration은 연결 준비 등을 제외하며, Windows curl time_total과 동일한 측정 구간이 아니다. 각 측정 경로의 기준선을 구분한다.

## 4. 단계 부하 결과

실행 ID: `k6-steps-20261003T013655Z-26656`.
ID 생성 시각은 2026-10-03 10:36:55 KST이며 요청 실행 시작과 정확히 같은 시각은 아니다.
계획 구간 합계는 200초이며 마지막 출력은 2,080 complete / 0 interrupted였다.

| 구간 | 계획 시간 | 완료 | 실패 | 평균 ms | p95 ms | 계획 시간당 완료율 근사치 |
|---|---:|---:|---:|---:|---:|---:|
| steady_1 | 60초 | 213 | 0 | 82.554776 | 83.220184 | 3.55건/초 |
| ramp_3 | 10초 | 58 | 0 | 82.271524 | 82.609354 | 5.80건/초 |
| steady_3 | 60초 | 636 | 0 | 82.706916 | 83.690923 | 10.60건/초 |
| ramp_5 | 10초 | 128 | 0 | 83.663963 | 84.273523 | 12.80건/초 |
| steady_5 | 60초 | 1,045 | 0 | 83.013405 | 84.233132 | 17.42건/초 |

1 VU 대비 5 VU의 유지 구간 완료율은 약 4.906배다. p95 증가는 약 1.013ms다. 합계는 213+58+636+128+1045=2080건이다.

완료율은 각 구간의 요청 수를 계획 시간으로 나눈 근사치다. 요청은 시작 시각의 단계에 배정되어 경계를 넘어 완료될 수 있고 실행 종료 유예도 있어 정확한 시각 기반 RPS는 원시 points가 필요하다. 단계별 p95를 평균 내 전체 p95로 사용하지 않는다.

## 5. 자원 관측의 한계

제공된 docker stats에서 order-api는 CPU 0.01%, 메모리 28.78MiB/512MiB, payment는 CPU 0.01%, 메모리 26.18MiB/512MiB였다.

해당 화면에는 임시 k6 컨테이너가 없고 캡처 시각도 없어 시험 종료 후일 가능성이 높다. 이를 3·5 VU 부하 구간의 CPU·메모리 또는 최고 사용량으로 기록하지 않는다. 생성기 CPU 포화, 대상 CPU throttling, 부하 중 메모리 추세는 미검증이다.

## 6. 자료 보존 범위

사용자 실행 환경은 `.local/k6-results/`에 실행 ID별 summary.json, points.json, console.log를 쓰는 구성이다. 콘솔에는 JSON 출력 경로가 표시됐으며 파일 쓰기 오류는 보이지 않았다. 해당 파일 자체는 이번 대화에서 전달되지 않았으므로 내용과 완전성을 확인하지 않았다. 이 문서는 제공된 콘솔 요약을 보존하며 전체 원시 메트릭을 대체하지 않는다.

파일 위치 예: `.local/k6-results/k6-steps-20261003T013655Z-26656.summary.json`.

## 7. 완료·미실행 구분

- 완료: 생성기 컨테이너 실행, 요청·본문 검증, smoke 2회, 단계 부하, 결과 해석.
- 미실행: spike, soak, 최대 처리량 탐색, 스트레스 한계 초과.
- 미검증: 제한값 전체 적용, 중단 기준 실제 발동, 부하 중 자원 추세, 장기 메모리 누수, 부하 종료 후 별도 주문 및 관측 경로 확인.
- 최신 실험에서는 마지막 5 VU 구간도 오류 없이 완료됐다. 다만 종료 후 별도 회복 요청 증거는 제공되지 않았다.
- 추가 파일 설치 후 사용자 로컬 Git 상태·커밋 여부는 확인하지 않았다.
