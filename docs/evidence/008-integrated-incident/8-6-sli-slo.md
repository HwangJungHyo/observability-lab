# 8-6 기존 결과로 이해하는 SLI·SLO·오류 예산

작성일: 2026-10-03. 새로운 부하나 장애를 주입하지 않고 기존 표본으로 해석한다.

## 1. 개념

| 개념 | 질문 | 이 실습의 예 |
|---|---|---|
| SLI | 실제로 어느 정도 품질을 제공했나? | 관측한 주문 성공 수 / 유효한 주문 시도 수 |
| SLO | 어느 기간에 어느 품질을 목표로 하나? | 예시: 30일 이동 구간의 주문 성공률 99.9% 이상 |
| 오류 예산 | 목표 아래로 내려가지 않는 범위에서 얼마의 실패를 허용하나? | 99.9% 목표라면 해당 기간 요청의 0.1% |

수집 성공을 뜻하는 up는 고객의 주문 성공을 대신하지 않는다. 8-3에서는 order-api up=1인 상태에서도 주문이 502로 실패했다.

## 2. 측정 범위와 성공의 정의

이번 k6 단계 부하의 유효 요청은 생성기가 보낸 합성 POST /orders 요청이다. HTTP 201, confirmed, amount 일치, 주문·결제 ID가 모두 정상인 경우 성공으로 판정했다. 통신 실패·timeout·잘못된 응답 본문은 실패로 포함한다.

이 검증은 합성 서비스의 응답 계약을 확인한 것이며 실제 결제 원장의 정확성이나 실제 고객 전체 경험을 측정한 것은 아니다. order-api와 payment 요청 수를 더하면 한 주문을 두 번 셀 수 있으므로 주문 경계에서 센다.

운영 SLO에서는 사용자 요청의 측정 위치, 유효 요청 정의, 재시도 취급, 4xx의 정당한 거부 여부, 측정 누락과 요청 0건 구간의 처리까지 사전에 정해야 한다. 서버에 도달하지 못한 요청은 서버 카운터에 없을 수 있다. 지표 누락을 성공으로 채우지 않는다.

## 3. 실제 계산 가능한 SLI

### 단계 부하의 업무 성공률

```text
관측 주문 시도: 2080건
성공: 2080건
실패: 0건
SLI = 2080 / 2080 × 100 = 100%
```

이 수치는 약 200초의 단일 시험 표본에 대한 결과다. 일·월 단위 가용성을 증명하거나 별도의 장애 주입 실험을 합쳐 기간 SLI로 사용할 수 없다. 운영에서 의도적으로 주입한 장애라도 측정 범위에 들어온 실제 고객 영향은 편의대로 제외하지 않는다.

### 지연 SLI는 성공률과 따로 본다

8-2의 1초 지연 실험은 HTTP 201 / curl 종료 코드 0 기준 134건 모두 성공했지만 평균은 1002.655ms였다. 성공 여부만 보면 지연 악화를 놓친다. 당시 반복 스크립트는 모든 응답 본문을 검증하지 않았으므로 k6 업무 성공 기준과 구분한다.

예시 지연 SLI는 다음과 같이 정의할 수 있다.

```text
빠른 성공률 = 정상 응답이면서 정한 측정 시간 200ms 이내인 요청 수 / 전체 유효 요청 수
```

200ms는 학습용 예시다. 실제 목표는 고객의 업무 요구와 측정 위치를 근거로 합의한다. 브라우저 전체 소요 시간, curl time_total, k6 http_req_duration, 서버 처리 시간은 서로 같은 지표가 아니다.

| 자료 | 판정 가능한 내용 | 판정할 수 없는 내용 |
|---|---|---|
| k6 단계 부하 요약 | 5 VU 구간 p95 약 84.233ms | 2080건 중 정확히 몇 건이 200ms 이하였는지 |
| 8-1 IPv4 원본 CSV 232건 | 모두 HTTP 201/종료 코드 0, 모두 time_total 200ms 이하; 최대 96.818ms | 모든 본문의 confirmed·업무 정확성 |
| 8-2 지연 실험 시간값 | 최소 985.848ms로 134건 모두 200ms 초과 | 운영 30일의 지연 목표 달성 여부 |

p95는 빠른 요청 비율 99%를 증명하지 않는다. 정확한 지연 비율은 해당 측정값의 원본 또는 목적에 맞는 버킷·카운터가 있어야 한다. 현재 서버 histogram에는 0.2초 버킷이 없고 0.15·0.25초가 있으므로 기존 버킷만으로 정확한 200ms 비율을 얻을 수 없다. 또한 현재 histogram에 상태 코드가 없어 성공 조건과 지연 조건의 교집합을 임의로 계산하지 않는다. 이를 위해 새 시험은 실행하지 않는다.

## 4. SLO를 제안하는 방법

| 항목 | 학습용 초안 |
|---|---|
| 업무 | 주문 생성 |
| 기간 | 최근 30일 이동 구간 |
| 성공 목표 | 유효한 주문 요청의 99.9% 이상 성공 |
| 지연 목표 | 유효한 주문 요청의 99% 이상이 합의한 클라이언트 관측 위치에서 200ms 이내 정상 완료 |
| 측정 범위 | 오류·통신 실패 포함, 유효 요청 정의와 누락 처리 사전 합의 |
| 현재 상태 | 설명용 가정. 운영 합의·수집 구현·30일 준수 검증 전 |

목표를 관측된 평균 83ms에 그대로 맞추지 않는다. 평균은 일부 느린 요청을 가릴 수 있고 지금 PC의 합성 서비스가 운영 환경을 대표하지 않는다. 성공 SLO와 지연 SLO는 각각 다른 예산을 가지며 하나를 충족했다고 다른 하나를 충족한 것은 아니다.

## 5. 오류 예산 계산

```text
허용 실패 비율 = 1 - SLO 목표
허용 실패량 = 같은 평가 기간의 전체 유효 요청 수 × 허용 실패 비율
예산 소모율 = 실제 실패량 / 허용 실패량 × 100
```

### 이해를 위한 운영 예시

30일에 유효 요청 100000건, 성공률 목표 99.9%라면 허용 실패량은 100건이다. 실패 20건은 예산의 20%를 사용하고 80건에 해당하는 여유를 남긴다. 이 숫자는 실제 운영 결과가 아닌 예시다. 이동 구간에서는 요청·실패가 창 밖으로 나가며 예산도 계속 바뀐다.

### 이번 2080건에 목표를 가정해 보기

2080 × 0.001 = 2.08건이다. 실제 건수는 정수이므로 이 고정 표본에서는 실패 2건까지 99.9%를 충족한다.

| 실패 수 | 성공률 | 허용 실패량 2.08건 대비 소모율 | 99.9% 가정 목표 |
|---|---:|---:|---|
| 0건: 실제 관측 | 100% | 0% | 표본 내 충족 |
| 1건: 가정 | 99.9519% | 48.08% | 충족 |
| 2건: 가정 | 99.9038% | 96.15% | 충족 |
| 3건: 가정 | 99.8558% | 144.23% | 초과 |

과거 502·504 한 건씩을 이 표본에 섞어 실제 실패 2건으로 계산하지 않는다. 실행과 분모가 다르다. 요청 기반 예산 0.1%를 고정 장애 허용 시간으로 변환하지도 않는다. 트래픽이 많은 시간의 장애와 적은 시간의 장애는 실패 요청 수가 다르다.

## 6. 예산으로 어떤 결정을 내리는가

예산이 빠르게 소모되면 영향 범위와 원인을 조사하고 위험한 변경을 줄인다. 예산을 소진했다면 새 기능보다 안정성 개선을 우선하는 정책을 고객·개발·운영 책임자가 합의한다. 목표 수치만 정하고 후속 조치가 없다면 운영 판단에 활용하기 어렵다.

8-5의 자동 중단 값(누적 실패율 5%, p95 1초, 30초 이후 평가)은 PC 실습의 중단 규칙이다. 30일 SLO나 운영 경보 조건이 아니다. 9장에서는 대상 수집 실패·업무 오류·지연을 구분하고 실제 대응할 경보와 Runbook을 구성한다. SLO 기반 소모율 경보는 측정 정의와 창을 확정한 뒤 설계한다.
