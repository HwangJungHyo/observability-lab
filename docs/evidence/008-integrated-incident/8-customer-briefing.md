# 8장 고객 설명 대본

작성일: 2026-10-03. 대상: 서비스 담당자·고객 운영팀.
아래 본문은 약 2~3분 분량으로 구성했다. 실제 낭독 시간은 측정하지 않았다.

## 발표 본문

이번 실습에서는 주문이 느려지거나 실패했을 때 문제 구간을 찾고, 조치 후 실제 주문이 정상으로 돌아왔는지 확인하는 과정을 검증했습니다. 시험 대상은 별도로 구성한 주문·결제 서비스입니다.

먼저 정상 응답 시간을 약 83밀리초로 측정했습니다. 결제 처리를 1초로 늦추자 주문은 성공했지만 응답도 약 1초로 늘어났습니다. 이를 통해 성공률과 응답 속도를 함께 관리해야 한다는 점을 확인했습니다.

결제 서비스를 중지했을 때는 주문 서버가 실행 중이어도 주문이 실패했습니다. 메트릭으로 수집 상태를 확인하고, 요청 ID로 로그를 찾은 뒤 트레이스로 실패한 호출을 좁혔습니다. 별도 재현에서는 이름 조회 실패를 확인했고, 결제 응답이 2초 제한을 넘는 경우에는 시간 초과 오류가 발생했습니다. 각 실험을 복구한 뒤에는 실제 주문이 성공하고 응답 시간이 약 80~90밀리초로 돌아오는 것도 확인했습니다.

부하 시험은 별도 컨테이너에서 가상 사용자 수를 1명, 3명, 5명으로 늘려 진행했습니다. 총 2080건이 응답 본문 검사까지 모두 통과했습니다. 각 유지 구간의 95번째 백분위 응답 시간은 약 83~84밀리초였습니다. 이번 시험 범위에서는 요청량이 늘어도 뚜렷한 성능 저하가 없었습니다.

품질 관리 기준도 정리했습니다. SLI는 실제 측정한 품질이고, SLO는 합의할 목표입니다. 예를 들어 성공률 목표가 99.9%라면 실패에 허용되는 비율은 0.1%이며, 이를 오류 예산이라고 합니다. 이번 표본의 성공률은 100%지만 운영 기간 전체의 목표 달성을 증명하는 수치는 아닙니다.

이번 성과는 장애 증상과 실패 구간을 근거로 연결하고, 업무 복구까지 확인하는 절차를 확보한 것입니다. 최대 처리량과 장기 안정성, 자동 경보는 아직 검증하지 않았습니다. 다음 단계에서는 주문 실패와 지연을 감지하는 경보, 담당자 통보, 복구 절차를 문서화한 Runbook을 연결하겠습니다.

## 발표자 참고: 읽지 않는 부분

- 정상 curl과 k6는 접속 경로와 측정 구간이 다르다. 두 수치의 유사성을 같은 측정이라고 설명하지 않는다.
- 약 83~84ms는 유지 구간별 p95다. 전체 2080건의 p95를 새로 계산한 수치가 아니다.
- 5 VU는 5명의 가상 사용자가 반복 요청하는 조건이며 운영 사용자 5명 또는 고정 초당 요청 수와 같지 않다.
- 자원 제한 전체 적용, 자동 중단 발동, 부하 중 자원 최고치와 종료 후 별도 복구 요청은 미검증이다.
- 이름 조회 실패는 별도 재현에서 확인했다. 앞선 모든 502의 원인이 확정됐다고 설명하지 않는다.
- 자동 경보의 구성·수신·해제는 다음 장의 과제다. 이번 복구는 수동으로 수행했다.
