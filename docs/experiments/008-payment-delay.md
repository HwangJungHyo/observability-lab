# 실험 008 — 오류 없이 발생하는 결제 지연과 원복

[챕터 지도](../roadmap.md) · [실행 가이드](../chapters/04-payment-delay.md)

## 목적과 환경
결제 서비스를 실행한 상태로 모의 대기를 0.08초에서 1초로 변경하고,
오류율이 0%여도 주문 응답이 느려질 수 있음을 확인한다.
Windows Git Bash + Docker Desktop, lab/004-order-api.
지연 기능 소스 fd28289, 대시보드 595bbb5.
2026-09-18 대화에서 제공한 Grafana 화면 2개와 최종 터미널 출력을 근거로 작성했다.
Grafana 구간 시각은 화면 표시 기준이며 날짜·시간대는 캡처 자체에서 확정할 수 없다.
원본 이미지와 전체 요청 로그는 이 문서에 첨부하지 않았다.

## 조작
PAYMENT_DELAY_SECONDS=1로 payment만 재생성한 실험 절차를 사용했다.
1초는 기존 80ms를 대체하는 모의 대기이며 운영 임계값이 아니다.
sleep은 의존 서비스의 대기를 모사하며 실제 CPU 병목이나 네트워크 지연을 재현하지 않는다.
명령은 실행 가이드에 기록돼 있다.

## 관측 결과

| 항목 | 지연 구간 (화면 약 10:32~10:36) | 이후 정상 수준 구간 (약 11:18~11:20) |
|---|---|---|
| 요청량 | 약 0.4 req/s | 약 0.6 req/s까지 상승 |
| 5xx 오류율 | 요청 있는 구간 0% | 0% |
| 평균 서버 처리 시간 | 약 1.01~1.05초 | 약 86~87ms |
| p95 추정값 | 약 1.95초 | 약 99ms |

평균 지연은 약 12배 증가했지만 5xx 오류율은 0%였다.
지연 구간 전체 HTTP 코드 출력은 제공되지 않았다. 오류율 0%만으로 모든 요청이 201이었다고 단정하지 않는다.
순차 요청은 응답 완료 후 1초 쉬므로 지연이 커질수록 발생 요청 수가 줄어든다.
이는 최대 처리량 시험이 아니다.

## p95 해석
Histogram의 1~2초 버킷에 대부분의 표본이 있으면 p95는 약 1.95초로 추정될 수 있다.
모든 표본이 해당 구간에 있다고 가정한 계산은 1 + (2 - 1) × 0.95 = 1.95초다.
실제 개별 요청이 1.95초 걸렸다는 증거는 아니다.
정상 구간 약 99ms 또한 75~100ms 버킷 해상도의 영향을 받는다.

## 최종 원복 증거

사용자 실행:

~~~bash
docker compose -f compose.yaml -f compose.orders.yaml exec -T payment printenv PAYMENT_DELAY_SECONDS
curl -sS --max-time 5 -w '\nHTTP %{http_code} duration=%{time_total}s\n' -X POST http://localhost:18080/orders -H 'Content-Type: application/json' -d '{"amount":10000}'
~~~

제공된 출력의 핵심:

~~~text
0.08
status=confirmed, amount=10000 (JSON 응답에서 발췌)
HTTP 201 duration=0.292710s
~~~

서버의 이동 평균 86~87ms와 curl의 개별 total 292.710ms는 측정 범위·표본·집계 구간이 다르다.
차이를 특정 네트워크 원인으로 확정하지 않는다.

시간 필드의 X로 고정을 해제한 뒤 현재 시각에서 up{job=~"order-api|payment"}를 다시 조회한다.
후속 대화에서 사용자가 현재 시각 두 값이 1임을 확인했다. 4-4 종료 체크를 완료했다.
