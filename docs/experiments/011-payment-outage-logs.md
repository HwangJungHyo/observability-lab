# 011 — 결제 중단과 복구의 JSON 로그 분석

날짜: 2026-09-18. 환경: 사용자 Windows / Docker Desktop / Git Bash.
근거: 사용자 터미널 출력, Grafana 장애 로그 화면, 복구 JSON 두 줄.
원본 로그 파일을 수집한 기록은 아니며 아래 값은 공유된 증거의 전사다.

## 실행과 결과

장애 요청 ID: down-1789715649-4591.
HTTP 502 / payment_unavailable 응답과 같은 ID의 오류 로그를 확인했다.
ps 결과: payment Exited (137), order-api healthy. 이후 payment start 실행.

복구 두 로그의 request_id: recovered-1789715817-19671.
장애 조회 화면에는 해당 ID의 주문 로그 한 줄이 표시됐다.
복구는 같은 ID의 주문201·결제200으로 업무 경로 성공을 확인했다.
두 완료 로그의 시각이 같아도 병렬 수행의 증거가 아니다. 기록 시각의 정밀도는 밀리초다.

## 판단

- 주문 프로세스 healthy만으로 주문 기능 성공을 보장하지 않는다.
- 직접 실행한 결제 중단, 컨테이너 상태, 주문 응답, 오류 로그를 교차 확인했다.
- payment 로그 부재만으로 원인을 단정하지 않는다.
- Exited (137)만으로 OOM이라고 판단하지 않는다.
- 복구 주문 시간에는 결제 시간이 포함된다. 차이 1.630ms는 순수 네트워크 지연으로 단정할 수 없다.
- 단일 요청 83.031ms는 평균·p95·용량 검증 결과가 아니다.

## timeout=2와 약 4초의 차이

app.py의 urlopen timeout은 연결 시도 같은 블로킹 작업에 대한 설정이다.
전체 주문 처리의 절대 마감시간 2초를 구현한 것은 아니다.
duration_ms는 요청 본문 처리부터 결제 호출 및 응답 처리까지 측정한다.
이번 오류는 코드에서 타임아웃으로 분류된 504/payment_timeout이 아니라 502/payment_unavailable이다.
실제 URLError.reason과 DNS/연결 구간별 시간은 기록하지 않았으므로 4초의 정확한 원인은 미확정이다.
2초 재시도 두 번, DNS 지연 등으로 단정하지 않는다. 필요하면 별도 계측으로 검증한다.
근거: https://docs.python.org/3.12/library/urllib.request.html#urllib.request.urlopen

## 완료 범위와 남은 확인

5-3 장애·복구 로그 조사와 기록은 완료했다.
이번 실험 시간대의 Prometheus up 변화와 오류율 그래프는 아직 사용자 증거로 확인하지 않았다.
5장 종료 전 마지막으로 현재 두 대상 up=1 및 실험 시간대 메트릭을 대조한다.
장애 요청이 한 건이므로 오류율이 반드시 100%이거나 복구 즉시 0%일 것으로 가정하지 않는다.
원복 주문201·결제200은 확인했으며 추가 장애 주입은 필요 없다.
