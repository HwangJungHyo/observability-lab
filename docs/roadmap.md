# Observability Lab 챕터 지도

## 목적과 진행 방식

주문 서비스의 이상을 감지하고, 영향을 파악하고, 원인을 추적하고, 복구를 입증한다.
도구 설치가 아니라 하나의 운영 질문에 답할 수 있는 범위를 챕터로 정한다.
한 세션은 60~90분을 가정한다. 시간은 계획 추정치이고 실제 수행 시간 측정값이 아니다.

완료 기준: 구조 설명 가능 → 소스 재현 가능 → 정상·이상·복구 검증 → 증거·한계·원복 기록.
실험 번호 001~016과 챕터 번호는 별개다. 실험 문서는 각 챕터의 증거로 연결한다.

|---|---|---|---|---|
| 1 수집 기반 | 대상 메트릭을 가져오는가? Compose·Prometheus·Grafana·Git | up=1/0 비교와 원복 | 1~2 | 실습 완료 |

2026-09-17 학습 순서 조정: LGTM 연결을 먼저 완성하고 임계값 도출은 8장에서 수행한다.
다른 Windows PC의 실제 재현, 엄격한 이미지 버전 고정은 아직 완료하지 않았다.
CPU 실습의 15%는 기능 검증용이며 운영 성능 임계값이 아니다.

## 모든 챕터의 공통 흐름

목표 정의 → 현재 상태 확인 → 구성 → 정상 검증 → 부하·장애 실험 → 복구 → 증거 기록 → 실습 설정 정리.
실행 성공 전에는 완료로 기록하지 않는다. 알림 수신과 프로그램 로그, 추정과 실측을 구분한다.
한 번에 다음 실행 단계만 안내하고 그 결과를 확인한 후 이어간다.

## 2026-09-22 개정: Mimir를 사용하는 실무형 과정

사용자 원칙: 모든 테스트는 가능한 범위에서 실무와 같은 절차로 수행한다.
로컬 규모는 축소하되 변경 전 기준선, 성공 조건, 중단 조건, 복구 절차, 증거 기록을 생략하지 않는다.
이미 완료한 1~6장은 기능 실험 완료로 유지하며 운영 부하·가용성 검증 완료로 소급하지 않는다.

### 공통 시험 계약

각 실험 시작 전에 다음을 기록한다.

1. 환경: Git SHA, 이미지 버전/digest, Docker 자원 한도, 수집 주기, timeout/retry, 데이터 보존 설정.
2. 가설·기준선: 어떤 장애를 주입하면 어떤 HTTP·메트릭·로그·span이 바뀌는지 예상하고 정상 트래픽을 측정.
3. 트래픽: 요청률·동시성·지속 시간·요청 수·데이터 분포를 고정. 단일 curl은 기능 확인에만 사용.
4. 변경: 한 번에 하나의 장애를 주입하고 시각·영향 범위를 기록. 반복 주문은 멱등성/중복 처리 영향을 먼저 검토.
5. 중단·복구: 자원 고갈·예상 밖 영향 시 중단 기준과 원복 명령을 사전 준비. 정상 요청·수집·로그·트레이스 복귀 확인.
6. 증거: 부하 원시 결과, HTTP 분포, p50/p95/p99와 표본 수, 카운터 증가량, 로그·트레이스, 복구 시간을 함께 기록.
7. 판정: 통과/실패/미측정 및 환경 한계를 구분. 동일 조건 반복으로 재현성을 확인하고 실제 실행 횟수를 기록.

초기 부하 시간 예시: 기준선 5분 → 장애 주입 1분 → 복구 관측 5분, 동일 조건 3회.
이는 계획 예시이며 수집·평가 주기, 장비 여유, 데이터량에 따라 실행 전에 조정한다.
적은 표본의 p99는 안정적 성능 기준으로 쓰지 않는다. 단일 PC 테스트는 물리 노드·가용영역 장애를 입증하지 않는다.

### 7장: Mimir 중앙 저장과 전송 복원력

- 7-0 사전 설계: Docker 가용 CPU/RAM/디스크 확인, 이미지 버전 고정, 배포 모드와 수집 아키텍처 선택을 ADR로 기록.
- 7-1 구성: Prometheus 수집·로컬 저장 유지, remote_write로 Mimir 전송, Mimir의 S3 호환 오브젝트 스토리지 연결, Grafana 데이터 소스 provisioning.
- 7-2 정합성: 동일 tenant·라벨·명시적 시간 구간·PromQL로 Prometheus와 Mimir 대조. 전송 지연이 가라앉은 후 카운터/시계열·샘플 타임스탬프 비교.
- 7-3 전송 장애: 합의한 짧은 시간 Mimir 수신 경로 중단, Prometheus 수집 지속 여부·pending/retry/failed·전송 지연 관측. 복구 후 큐 해소와 장애 구간 데이터 도착 확인.
- 7-4 영속성: 블록이 실제 오브젝트 스토리지에 업로드된 것을 확인하고 재시작 전후 과거 범위 조회. 재시작 성공만으로 장기 보관·백업 복구 완료로 판정하지 않는다.
- 7-5 테넌트: 동일 메트릭명으로 tenant A/B 분리 확인. tenant 헤더 자체를 인증으로 취급하지 않으며 운영 인증·인가 경계는 10장에 구현/검증.
- 7-6 정리: 로컬 보존과 중앙 보존 정책, 용량·카디널리티, 유실 가능 구간과 운영 한계를 기록.

기본 로컬 구성은 monolithic + 영속 볼륨 + S3 호환 스토리지로 시작한다.
이는 개발·학습용 출발점이다. 운영 분산 배포는 11장에서 다룬다.
Mimir 버전과 classic/ingest-storage 선택은 별개로 명시하고, ingest-storage 선택 시 Kafka 등 필요한 의존성·자원까지 포함한다.
구체 이미지·포트·설정은 7-0에서 확정한다. latest를 무검증 사용하지 않는다.

remote_write 재전송은 무제한 보장이 아니다. 선택한 Prometheus 버전의 WAL·큐 동작과 실제 장애 지속 시간을 기록한다.
로컬 TSDB 보존을 늘렸다는 이유로 모든 과거 데이터가 자동 재전송된다고 가정하지 않는다.
Mimir 전송 시작 전 과거 데이터 이관은 별도 backfill 작업으로 취급한다.

### 8장: 통합 장애 조사와 성능 기준

- 정상·단계 증가·급증·지속 부하를 실행하고 부하 발생기 자체의 포화도 확인.
- 결제 처리 지연, 서비스 중단, 연결 거부, 응답 timeout을 각각 제어해 구분.
- 기존 약 4초 실패를 DNS·연결·재시도·대기 등 세부 시간으로 분해. 원문 오류/계측 없이 원인 확정 금지.
- 주문 성공률과 지연 SLI를 정의하고, 기대 트래픽·고객 요구에 근거해 SLO와 오류 예산 초안 작성.
- Mimir 메트릭 → Tempo 트레이스 → Loki 로그로 장애 타임라인 작성.
- 메트릭 exemplar → trace 연결은 계측·전송·저장 지원 설정을 확인한 후 별도 검증.
- 요청률·동시성·오류율·latency·CPU/RAM을 함께 보고 병목을 판단.

### 9장: 알림과 Runbook

- 초기에는 기존 Prometheus 규칙 + Alertmanager를 유지해 7장 변경 범위를 제한.
- 고객 영향 알림: 주문 실패율·지연·무트래픽 조건. 데이터 없음/수집 실패를 정상 0과 구분.
- 관측 시스템 알림: remote_write 지연·실패, Mimir/Loki/Tempo/Alloy 이상, 저장 공간.
- Mimir Ruler는 중앙 서비스 규칙을 위한 비교/이관 실험으로 추가. 규칙별 평가 주체와 데이터 의존성을 명시.
- Mimir 장애 감지는 Mimir 조회만 의존하지 않는 로컬 Prometheus 경로로 유지.
- 규칙 단위 테스트 → 실제 장애 주입 → FIRING 수신 → 조치 → RESOLVED 수신 검증.
- 같은 규칙을 두 평가기에 무심코 활성화하지 않는다. 이관 중 중복 알림, inhibition·silence·grouping도 확인.
- Runbook: 영향, 확인 쿼리, 판정, 조치, 복구 기준, 에스컬레이션, 증거 링크.

### 10장: 재현성·보안·변경·백업 복구

- 버전/digest 고정, 설정 검사·규칙 테스트·비밀정보 검사 CI.
- PR의 검증된 커밋을 배포하고 변경 전후 스모크 테스트, 실패 시 rollback.
- 새 경로/새 환경 재현. 기존 볼륨에 의존한 우연한 성공과 구분.
- 인증·인가·TLS·비밀정보 분리·최소 권한을 적용 가능한 경계에서 검증.
- 설정·Grafana 상태·오브젝트 스토리지 등의 복구 범위 정의, 별도 복구 환경에서 실제 복원.
- RPO/RTO 목표와 측정값 기록. 볼륨 유지 재시작은 백업 복원과 구분.

### 11장: 자원 여건에 따른 운영 확장

Kubernetes 분산 Mimir, 스토리지와 필요 시 Kafka, 복제·수집 HA 중복 제거, rolling update를 다룬다.
노드/AZ 분리가 가능한 환경에서 장애 허용을 검증한다.
한 PC의 다중 컨테이너·kind 노드는 프로세스 수준 검증이며 물리 장애 격리를 보장하지 않는다.
추가 클라우드 비용이 드는 배포는 환경·예산을 먼저 정한 후 진행한다.
